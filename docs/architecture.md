# Архитектура и безопасность

Статус: черновик фазы 2. Всё, что помечено **[прототип]**, надо проверить кодом до того, как считать решённым.

## Стек
- **Go, один статический бинарник** (панель + helper). Причины: ставится одним файлом, нет рантайма и Docker на хосте, легко подписывать и обновлять, мало памяти. PHP отпал: нужны БД, Redis и два процесса.
- **БД: SQLite** (WAL). Один файл, бэкапится вместе с панелью. Для одной ноды хватает.
- **Веб: серверные Go-шаблоны + htmx**, без Node-сборки. Консоль и статус через SSE. Причины: меньше кода, быстрее старт, меньше поверхность атак. Если интерактивность упрётся, добавим точечные островки JS.
- **i18n:** каталоги сообщений ru/en в репозитории.
- **Движок:** LinuxGSM (MIT) вызывается как внешний процесс, не вшивается в бинарник.

## Компоненты
```
[браузер] -> [panel (непривилегированный пользователь, HTTP/HTTPS)]
                  | unix-socket, узкий набор команд
                  v
             [helper (root, systemd)]  -> создаёт пользователей, ставит deps, запускает от имени
                                          пользователя игры: lgsm-скрипт, tmux, бэкап, chown
```
- **panel** не root. Всё, что требует прав, идёт через helper.
- **helper** принимает по сокету фиксированный список операций с проверенными аргументами (имя сервера по regex, шлюз до каталога сервера). Никаких «выполнить произвольную команду». Это ключевой ответ на классы уязвимостей Pterodactyl (CVE-2024-27102, CVE-2025-49132).
- Каждый игровой сервер работает под **своим Linux-пользователем** (так и делает LinuxGSM), домашний каталог `0700`. Полной контейнерной изоляции в MVP нет: в доках так и пишем: это не песочница уровня Docker. Опциональный запуск через systemd-слайсы/`ProtectSystem` на втором шаге **[прототип]**.

## Модель данных (минимум)
`users`, `sessions`, `api_tokens`, `servers` (имя, игра, linux-user, путь, режим: managed/adopted), `schedules`, `backups`, `audit_log`, `settings`, `license`.

## Файлы и path traversal
Единая функция доступа к файлам сервера в одном модуле: открывает файлы через `openat` относительно открытого дескриптора корня сервера (в Go `os.Root`, если версия позволяет), запрещает выход через `..` и симлинки, отказывает по белому списку расширений и каталогов для редактора. Все остальные пути в коде получают файлы только через этот модуль; тест с набором враждебных путей обязателен в CI.

## Аутентификация
- Пароли: argon2id. Сессии: HttpOnly, Secure, SameSite=Strict, ротация при входе. CSRF-токены на все изменяющие запросы.
- 2FA TOTP, коды восстановления. Лимиты попыток входа.
- API-токены с областями и сроком.
- Роли: owner (всё), admin (серверы, без пользователей и лицензии), viewer (чтение). Права проверяются на сервере, а не в шаблоне.
- Нет публичных эндпоинтов без авторизации, кроме страницы статуса (только чтение, узкая схема) и health.

## Обновления и подпись
- Релизы подписываются ключом (minisign/ed25519). Публичный ключ вшит в установщик и в бинарник. Приватный ключ никогда не в git, хранится у владельца (TODO).
- Установщик скачивает бинарник и подпись, проверяет подпись **до** установки; без неё отказ. Каналы stable/beta. Перед обновлением снимок бинарника и БД, при неудачном старте автоматический откат (watchdog в systemd). **[прототип]**
- Ограничение: `curl | bash` защищён подписью только если сам скрипт приходит по HTTPS с домена владельца; в доках дадим вариант «скачать, проверить, запустить».

## Лицензия
Онлайн-активация (ADR 0004). Панель отправляет ключ и отпечаток машины, сервер привязывает ключ к инстансу и отвечает подписанным (ed25519) токеном на 7 дней: тариф, лимиты, срок. Панель продлевает токен раз в сутки, при отсутствии связи работает на последнем токене и ещё 30 дней грейса. После грейса блокируются только новые Pro-действия, запущенные серверы, бэкапы и расписание не трогаем. Подпись токена проверяется вшитым публичным ключом, иначе поддельный сервер или правка файла обходили бы лицензию. Free-тариф к серверу не обращается. Открытый код можно пропатчить, от этого не защищаемся.

## Телеметрия
Только opt-in, анонимная (версия, число серверов, ОС), описание в панели и доках.
