# Безопасность лицензий и обращений к серверу

Статус: проект фазы 2/4. Дополняет ADR 0004. Пометка **[прототип]** означает «проверить кодом».

## 1. Что показали источники про возражения пользователей

Найдено мало первоисточников (поиск не вернул r/selfhosted), выводы осторожные.

- Реальные скандалы связаны с **телеметрией, включённой по умолчанию или добавленной без объявления**: Netdata (спорили, что IP делает данные не анонимными, Hacker News 2021), Audacity (отказались от плана после возмущения, разработчики признали, что плохо объяснили), Home Assistant (спорным был способ внедрения, сама функция opt-in), Immich (opt-out вызывает недовольство «dark pattern», сама телеметрия вопросов не вызвала) [1-4].
- Раздражает не обращение само по себе, а **неожиданность и невозможность выключить**. Страницы подбора self-hosted ПО прямо используют «никакой телеметрии» как критерий выбора [5].
- Прецеденты именно про проверку платной лицензии на выбранных мной примерах (Plex, Portainer) не нашлись. Есть только аналогии: у Autodesk при недоступности облачного лицензионного сервера пользователи не могли открыть ПО, у Sage 50 при простое активации не работали новые установки [6]. Уроки: нужен грейс-период и запрет блокировки работающего.
- Прямых данных «сколько процентов пользователей отказываются» нет. Реальный спрос проверим в Discord перед выпуском Pro.

**Что из этого следует для дизайна**
1. Free **вообще не обращается** к нашему серверу и не требует ключа.
2. Проверка лицензии идёт только если пользователь ввёл платный ключ. Это не телеметрия, и в UI это показано честно: кнопка «Что отправляется», последний отправленный пакет виден.
3. Проверка обновлений - отдельная настройка. Вопрос задаём явно при первом запуске (без значения по умолчанию, которое молча включает сетевой запрос). Критичные уведомления безопасности можно получить и без этого: GitHub Releases + баннер при следующем обновлении.
4. Телеметрия использования - отдельная настройка, opt-in, по умолчанию выключена.
5. Все три канала можно полностью отключить в `config.toml`, и тогда панель с платным ключом тоже работает (до конца токена + грейс).

## 2. Тариф Free

Free: всё открытое ядро без лимита серверов, без ключа и без связи с нашим сервером. Pro включает S3, откат обновлений, роли и другие функции по токену. Цены - позже.

## 3. Модель угроз

| Кто | Чего хочет | Что делаем |
|---|---|---|
| Пользователь, не желающий платить | Pro бесплатно | Не боремся с патчем кода (открытый код). Защищаем от «случайного» обхода: подписанные токены, привязка к инстансу, лимит активаций на ключ. Цена обхода выше цены ключа |
| Тот, кто украл/перехватил ключ | Использовать чужой Pro | Ключ случайный и хранится на сервере хешем, показ один раз; лимит активаций и оповещение владельца при дубле |
| Тот, кто хочет подделать ответ сервера (DNS, MITM, фальшивый сервер) | Выдать себе Pro | Токен подписан, панель принимает только подпись нашим ключом. TLS поверх; **cert pinning не делаем** (ломается при смене сертификата), опираемся на подпись |
| Тот, кто хочет вломиться в сервер лицензий | Выдавать ключи, украсть данные | Раздел 5. Корневой ключ подписи не лежит на сервере |
| Скомпрометированный `issuer` | Раздать ключи | Роль без отзыва и финансов, квота в сутки, обязательный номер заказа, журнал |
| Тот, кто хочет атаковать нас через канал обновлений | RCE на панелях пользователей | Раздел 6. Сервер лицензий не может присылать команды или код |
| Злоупотребление нашим сервером | DoS активаций, перебор ключей | Лимиты запросов, ключи 128 бит, одинаковый ответ при ошибках |

## 4. Ключи и токены

**Лицензионный ключ.** Случайные 128 бит (CSPRNG) + контрольная сумма для опечаток, показывается один раз. В БД сервера хранится только SHA-256 ключа. Утечка БД не раскрывает рабочие ключи. Ключ - ссылка на запись на сервере, а не самодостаточный документ (в отличие от самоподписанного ключа из старого плана).

**Активация.** Панель при первом вводе ключа генерирует **пару ключей инстанса (ed25519)**, закрытая часть остаётся в БД панели (файл `0600`). Запрос на активацию подписывается ключом инстанса, в нём публичная часть, версия панели, nonce. Сервер привязывает ключ лицензии к публичному ключу инстанса. Отпечаток по `machine-id` мы **не используем как единственную привязку**: он подменяется и меняется при клонировании VM; максимум добавляем как подсказку для лимита.

**Токен.** Свой компактный формат, не JWT (чтобы не получить класс багов «алгоритм из заголовка»). Поля: `v`, `kid`, `jti`, `iat`, `exp`, `inst` (публичный ключ инстанса), `plan`, `limits`. Алгоритм жёстко ed25519, неизвестные `v` и `kid` отклоняются. Срок 7 дней.

**Проверки в панели при каждом чтении токена:** подпись ключом из вшитого списка, `inst` совпадает с нашим ключом инстанса, срок не истёк (с учётом грейса), `iat` не из будущего более чем на 5 минут.

**Часы.** Панель хранит максимальный виденный `iat`. Если локальное время меньше этого значения, считаем текущим временем сохранённое максимальное, и перемотка часов назад не продлевает токен. Перемотка вперёд лишь быстрее заканчивает токен. Идеально не защищает (можно стереть БД), но ломает простейший обход **[прототип]**.

**Повтор токена.** Токен привязан к `inst`, украденный токен на другой панели не пройдёт. Обновление токена идёт с подписью ключа инстанса и nonce, сервер хранит последний nonce.

**Лимит активаций.** Pro: 1 инстанс на ключ по умолчанию, перенос на новый через админку/самообслуживание с задержкой. Сервер замечает, что один ключ обращается с двух разных инстансов одновременно, и помечает для владельца, ничего не блокируя автоматически (ложные срабатывания при миграциях).

**Отзыв.** Флаг в БД сервера. Вступает в силу при следующем продлении (до 24 ч) или максимум к концу токена (7 дней). Мгновенного отзыва нет, это осознанный компромисс.

## 5. Сервер лицензий и админка

**Иерархия ключей подписи.**
- **Корневой ключ** (ed25519) хранится офлайн (аппаратный ключ или зашифрованный носитель у владельца, две копии в разных местах). Подписывает только сертификаты онлайн-ключей и релизы.
- **Онлайн-ключ подписи токенов** на сервере, срок 90 дней, сертификат подписан корневым. Утечка онлайн-ключа не ведёт к потере корня: выпускаем новый, старый выводим через список отозванных `kid` в следующем релизе панели и в ответах сервера.
- В панель вшито **два корневых публичных ключа** (основной и резервный) для ротации без катастрофы.

**Админка.** Отдельный поддомен, вход только с 2FA/passkey, по возможности доступ с разрешённых IP или через VPN. Сессии короткие, CSRF, заголовки безопасности. Роли: owner, issuer (ADR 0003). Каждое действие пишется в журнал; журнал append-only с хеш-цепочкой, чтобы сотрудник не мог тихо стереть следы. Выдача требует **номер заказа** (Boosty/FunPay), уникальный: нельзя выдать два ключа на один заказ. Квота на issuer в сутки. Отзыв, возврат, смена тарифа - только owner.

**Платформа.** Сервер лицензий отдельно от сайта, минимальные права процесса, бэкапы БД шифруются, секреты только в окружении/менеджере, не в репозитории. Ограничения запросов на IP и ключ, одинаковый ответ на «нет такого ключа» и «неверный ключ» (без перечисления), логи без ключей в открытом виде. Обновления ОС и зависимостей по расписанию.

**Персональные данные.** Храним минимум: хеш ключа, публичный ключ инстанса, версию панели, время обращений, IP с сроком хранения 30 дней, контакт покупателя (ник/почта) только по необходимости выдачи. Описание в политике ПДн (фаза 6).

## 6. Что сервер лицензий НЕ может

Сервер возвращает **только подписанный токен и список отозванных `kid`**: данные, не команды. Никакого кода, скриптов, команд, конфигов, настроек панели. Это записано как правило архитектуры: компрометация нашего сервера не должна давать выполнение чего-либо на панелях. Обновление панели - другой канал: бинарник со своей подписью корневого ключа, версия строго растёт (откат версии только по явному действию пользователя), установка не происходит без подтверждения, пока пользователь не включил автообновления.

## 7. Fail-safe в коде

- Любая ошибка лицензии (подпись, часы, сеть, битый токен) приводит к режиму «как Free», а не к ошибке или остановке. Такой режим не удаляет данные и не отключает расписания.
- Подсистема лицензий не имеет вызовов, останавливающих игровые серверы. Проверка на уровне импортов и тест: пакет `license` не зависит от пакета `servers`.
- Тесты: подпись другим ключом, подмена `inst`, просроченный токен, откат часов, битый формат, неизвестный `kid`, недоступная сеть.

## 8. Открытые вопросы

1. Способ хранения закрытого ключа инстанса в БД: файл `0600` достаточно или шифровать мастер-ключом из системы **[прототип]**.
2. Процедура безопасной ротации и отзыва онлайн-ключа: расписать и прогнать на тестовом стенде до первого платного релиза.
3. Нужна ли повторная проверка конкретных формулировок о ПДн юристом (фаза 6).
